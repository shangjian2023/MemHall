# 第六章 工程实现与工具化

前三章交代了题库、剧本与判卷，本章回答另一个问题：别人怎么拿到它、装上它、并且相信它跑出来的数字。五个小节依次是工具封装（CLI、Web UI 与双平台发行包）、九适配器架构、统一模型网关、实验可信度工程、稳定性证据，对应评分维度里"工程可落地"与"稳定性与可复现"两块。

## 6.1 工具封装：一条命令、一个安装包

评测系统如果只能靠读源码复现，对社区用户就是一纸空文；openKylin 用户还要自己解决依赖版本与桌面集成。

本作品的方案是把全链路收进一条命令。`memhall run` 跑完即在 runs/<run_id>/ 下落齐六类产物：manifest.json（被测智能体版本、模型口径、token 记账、环境封存）、verdicts.jsonl、metrics.json、radar.png、report.md 与逐题证据 JSONL，每条判定都能下钻到证据哈希。发车前 `memhall doctor` 一键体检三路：本机（PATH、配置目录、版本）、评测机（SSH 单往返复合探测，含记忆库是否在位）、环境就绪度（密钥/SSH/网关可达）。跑完再一条 `memhall verify` 复核产物完整性（CLI 全产物链路图见第五章 图~cli-run~）。

发行物覆盖双平台。openKylin 侧是 .deb 安装包：注册 UKUI 应用菜单项，系统目录只读（run 产物写 ~/memhall-runs，配置读 ~/memhall.env，卸载一条 `dpkg -r` 清理干净）；依赖按 uv.lock 冻结清单以离线 wheels 打进包内，装机不联网；构建在 openKylin 目标机上原生完成，保证 wheel 与目标机 Python 精确匹配，同版本源码任何时间构建产物一致。Windows 侧是便携 exe：onedir 目录版启动快，单文件版可直发，双击即进 Web UI 原生窗口。如实交代进度：v2.0.0 单文件 exe 已完成打包，冒烟覆盖版本自检、doctor 体检与干净目录下一轮完整 mock 评测（产物 verify 通过）；v2.0.0 的 .deb 最终包正随目标机验收流程重建。openKylin 集成还有一个细节：评测收尾发 UKUI 桌面通知并自动弹出雷达图。装机与桌面形态见图~desktop~。

## 6.2 九适配器架构：同一把尺量四家

各家智能体的 CLI 形态、记忆存储、会话语义互不相通：有的写 Markdown 记忆文件，有的用 SQLite 记忆库，有的记忆是沙箱内的检索索引。如果为对比而各写各的驱动，比出来的实际是"适配器写得好不好"，不是记忆能力。

本作品的方案是全部车道经同一个 AgentAdapter 基类接入。适配器只做四件事——转发消息、导出记忆、导出操作、管理会话生命周期；不评判、不改写用例、不产生任何判定，评分层的事一件不碰。各家异构的记忆统一归一为 MemorySnapshot 中间格式（entries 列表），判卷器与被测对象彻底解耦——新增一个智能体等于新增一个适配器，题库与判卷零改动。隔离上，每条车道的评测沙箱家目录独立建立，不碰用户真实的 ~/.hermes、~/.openclaw 等配置与记忆；本机车道用各家官方支持的环境变量把"家"指进沙箱。

被测对象实接四家：hermes、kylinbot、openclaw 三家在 openKylin 虚拟机内实测联调；kylin-agent（赛题点名的系统智能体）是第九个适配器——其被测后端运行时是 Hermes 的 fork，我们以子类复用 hermes 车道的全部证据语义，再对 fork 源码逐条复核后覆写差异：家目录用环境变量钉进专属目录防止串写 Hermes 状态、非零退出码携带的输出一律降级为运行无效而不冒充计分答案、版本自报严判防止把 GUI 前端当命中。

> 诚实声明：kylin-agent 车道目前只有适配器接入与源码级复核，VM 真机验收仍在进行，尚无实测成绩；拿到真机验收记录之前不下"已联调"结论，也不引用同源车道的分数作任何推断。

## 6.3 统一模型网关：把"模型"变量钉成仪器

被测智能体若各用各的 LLM 后端，分数就混入了模型差异；更麻烦的是 HTTP 客户端跑在智能体进程里，"大家用同一个模型"只靠配置自觉，无从验证。

本作品的方案是统一车道流量必经本地网关（监听 8311），自研薄层实现，只依赖项目里已有的 fastapi/httpx，不新增打包负担。三条保证机制：其一，模型强制改写——请求体里的模型名一律替换为网关指定模型，智能体侧配置漂移无效；逐智能体的改写表按 memhall-<agent> 身份标签键控，发车时写入、收尾清理，由此构造 (agent, model) 二元组对照——相当于把"模型"变成同一台仪器，四家被测对象在同一台仪器上读数。其二，凭据单点——真上游 key 只存在于网关进程环境，智能体只拿形如 memhall-<agent> 的 dummy key；入站凭据兼作记账归因身份，绝不写日志、绝不转发给上游。其三，逐请求记账与节奏控制——每请求一行 JSONL（智能体、模型、token、耗时、状态码、重试数），转发最小间隔默认 8 秒，上游 429/5xx 指数退避并尊重 Retry-After，被测侧无感。原理如图~gateway~所示。
{{fig:gateway|统一模型网关原理|绘制中}}

对账是这套仪器的检定环节：网关按账单追加序号归因，逐场评测给出三态结论——verified（账实相符）、suspect（有疑点）、unknown（账单读不到，不冒充无告警）；拨过钟的用例也能精确对账。三态对账块随每场评测写入 manifest，聚合出数前逐场核对，对账未过的场进不了同一张榜。"必经网关"由此从配置约定升级为有"该来没来"检查的仪器。

> 设计取舍：claude 本机车道走 anthropic 协议，不进统一对照车道——配置了网关地址会显式报错，而不是静默绕过，把不可比的数混进榜里。

## 6.4 实验可信度工程

temporal 题型要拨系统时间，拨了恢复不干净，耗时与时间语义全失真；评测引擎与 Web UI 若并发发车，会互相踩掉对方的 reset；证据文件被人改动，传统方式无从发现。这些都是"数字可不可信"的地基问题。

本作品的方案是五组机制。①OS 级沙箱：bwrap 把被测进程整根文件系统只读挂载，白名单目录可写（智能体自家目录、用例注入工作区、题面产物根），/tmp、~/.cache、~/.npm 挂 tmpfs——每条消息独立、跨用例零残留，防止智能体把记忆性内容藏进"快照与 reset 都看不见"的缓存目录。沙箱默认关闭（不动冻结口径），MEMHALL_SANDBOX=1 显式开启，开关状态随运行环境记入 manifest 供后续口径校验。②拨钟恢复含单调耗时：首次拨钟前用同一条命令同时读墙钟与单调钟（/proc/uptime），恢复目标=基准时刻+单调增量，真实耗时不被拨钟白吃；发车前预检宿主与评测机钟差，超 ±300 秒拒跑。③UTC 口径：run 起点存发车时带时区的 UTC 时间，全链路账单与证据统一 UTC 写入。④run 互斥锁：~/.memhall/run.lock 跨进程互斥，CLI 与 UI 不能同时开跑。⑤封印审计与废轮留痕：`memhall verify` 对 run 目录做证据 schema 校验、payload SHA-256 逐条复算，封印类字段有则强校验、无则明确降级为警告，不把"没写封印"误报成"证据被篡改"；失败轮全量归档不删除，历史 run 与 manifest 不改写。

沙箱写面隔离的结构如图~sandbox~所示。这些机制合计有 18 项专项隔离守卫测试覆盖（互斥锁、拨钟往返与失败路径、错钟闸门、网关对账、reset 清旧），是第七章全部实验数据可信的前提。

## 6.5 稳定性证据

工程声明若不能机器复验，就只是 README 里的口号，所以本节只给可查的证据。

CI 双平台矩阵：ubuntu 与 windows × Python 3.11/3.12（3.11 对齐 Windows 开发环境，3.12 对齐 openKylin 3.0 目标机），每次提交与 PR 跑 ruff/mypy 静态检查、题库门禁、判卷金标准离线自检（错判零容忍）、全量测试。平台口径如实标注：GitHub 没有 openKylin runner，CI 矩阵属 Tier 2 证据；openKylin 真机特有的验证深度——重启存活、拨钟隔天、多用户隔离、断网存活（hermes 真机 4/4 通过）——以 runs 产物与系统级测试报告为证。测试规模：v2.0.0 全回归 378 项（基线 293 + 评审修复轮 80 + 盲评材料 4 + 判卷定版 1），另附离线 mock 端到端全链路（抽样→跑→verify→报告→聚合→实验索引统计）。可复现基建：冻结试卷（分层抽样、完整题目封存、SHA-256 校验，正式对比不依赖运行历史）；heldout 加试池公开 seed；生成器同 seed 可复现生成 1008 实例并保留模板与参数记录。汇总见表~t6-2-stability~。
