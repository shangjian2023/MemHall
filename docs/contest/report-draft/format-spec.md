# 参赛报告排版规范（对齐获奖范本实测值）

> 实测来源：`build/report-ref/yjs-report.docx`（中国研究生网络安全创新大赛获奖作品报告，43 图 + 14 表）。
> 本文件是全部报告模块的统一格式契约：写作用 markdown 方言，`tools/build_docx.py` 按本规范渲染为 Word。
> 单一真源：改格式只改本文件和 builder 常量，不改各模块源文件。

## 1. 页面与版心

| 项 | 值 |
|---|---|
| 纸张 | A4 纵向（21.0 × 29.7 cm） |
| 页边距 | 上 2.54 / 下 2.54 / 左 2.86 / 右 2.59 cm |
| 页眉/页脚距 | 1.5 / 1.75 cm；页脚居中放页码（合并整本时自动加） |

## 2. 字体字号（与范本逐项对齐）

| 元素 | 中文字体 | 西文字体 | 字号 | 其他 |
|---|---|---|---|---|
| 封面主标题 | 黑体 | — | 26pt | 居中，加粗 |
| 封面作品名行 | 黑体 | — | 16pt | 居中，加粗 |
| 一级标题（第X章） | 黑体 | Times New Roman | 16pt（三号） | **居中**，段前 17pt 段后 16.5pt |
| 二级标题（X.Y） | 宋体 | Times New Roman | 12pt（小四） | 加粗，左对齐 |
| 三级标题（X.Y.Z） | 宋体 | Times New Roman | 12pt（小四） | 加粗，左对齐 |
| 正文 | 宋体 | Times New Roman | 12pt（小四） | 1.5 倍行距，首行缩进 2 字符（0.85cm），两端对齐 |
| 图注/表注 | 楷体 | Times New Roman | 11pt | **居中**，行距 1.2，段前 3pt 段后 6pt；表注在表上方，图注在图下方 |
| 表格内文字 | 宋体 | Times New Roman | 11pt | 表头加粗居中；数据行居中；单元格行距 1.15 |
| 行内代码/命令 | — | Consolas | 10.5pt | 底纹浅灰 |
| 引用/提示块 | 楷体 | Times New Roman | 11pt | 左缩进 0.74cm，不首行缩进 |

**编号体系**（范本口径）：章号"第一章/第二章"中文数字；节号 1.1 / 1.1.1；**图、表全文连续编号**（图 1、图 2 …；表 1、表 2 …），由 builder 按 fig/tab 语义 ID 在整本中的出现顺序自动分配，模块里只写语义 ID，不写死编号。

## 3. markdown 方言（模块源文件语法）

```
# 第一章 作品概述                     ← 每模块一个 H1（或被合并进上一章）
## 1.1 研究背景与意义                 ← H2
### 1.1.1 xxx                        ← H3
正文段落。**加粗**、`命令`、〔待填：xxx〕     ← 段内空行分段；首行缩进自动
- 项目符号列表                         ← 无首行缩进
1. 编号列表                           ← 同上
> 提示/引用块                          ← 楷体缩进块，用于"设计取舍""诚实声明"类内容

{{fig:arch|麟阁总体架构|绘制中}}       ← 图占位：语义ID|图题|状态(绘制中/待截图/待出数/已就绪)
                                      ↑ PNG 到位后放 tools/../figures/<语义ID>.png 自动嵌入

【表:coverage|能力×内容覆盖矩阵】      ← 紧跟其后的 markdown 表格；表注自动"表N 图题"
| 列1 | 列2 |                          ← 普通表格；三线表样式由 builder 渲染
```

规则：
1. 每张图/表**必须被正文显式引用**（"如图 N-M 所示"按语义 ID 写成"如图~arch~所示"，builder 渲染时替换成实际编号）。
2. 待补数据一律 `〔待填：具体说明〕`（如"〔待填：D 全量矩阵 hermes 六维均值±标准差〕"），builder 渲染为灰色高亮，终稿前清零。
3. 数字纪律：所有可查数字（题量、测试数、诱饵数、CI 等）必须来自仓库现有文件（README/CHANGELOG/dataset-card/stats 输出），**禁止估算编造**；出处不确定就写待填或删掉。

## 4. 写作风格（从两份获奖范本提炼）

1. **口吻**："本作品/我们"，第一人称工程叙事；不用"笔者/本文认为"学术腔。
2. **段落节奏**（貔貅式三段论，每个技术小节都遵循）：①现状痛点（谁没做到什么）→ ②本作品方案（怎么设计、为什么这样取舍）→ ③效果证据（数字/图表/对照实验收尾）。
3. 段落 3–8 句；一段只讲一件事。忌术语堆砌，说人话但保留必要专业词。
4. 每章开头 1 段"本章导读"式引言（2–3 句，讲清本章在整体方案中的位置）。
5. **匿名**：全文不出现学校/姓名/导师名；贡献处写"团队"。
6. 特殊符号沿用范本习惯：步骤用 [第1步]、情形用 <情形1>、并列要点用 ①②③、子图用 。数学量用正体斜体一致的简洁写法，不排 LaTeX 源码。
7. **展示导向语气（2026-10-14 用户定版，取代旧"诚实优先"条）**：报告是向评委展示方案、效果、工程性与六个评审维度的作品文档——
   - **禁止自证/辩护式叙述**：删掉一切与假想质疑辩论的段落与措辞（"要如实说明""诚实边界""不宣称""不冒充""不硬判""不凑数""不写成 X""防 X 不防 Y""为什么不用 Y"）。工程取舍写成一句正面的设计理由（例："统计按模板聚类报告，口径独立严谨"），不做反方论证、不自我设限、不讨论自己"没做到什么"。
   - **事实性状态一句话带过**：必要的客观状态只允许一行中性陈述（如"kylin-agent 适配器已接入，真机验收与实测成绩随验收流程交付"），不展开辩护，不加"只有/尚无/如实交代/需要提前说明"式前缀。
   - **有力的机制描写保留**（例："断言用'曾经包含'，事后删除洗白不了"）——这是展示工程强度，不是自证。
   - 数字纪律与〔待填〕机制不变：所有数字仍须仓库可查；呈现为"效果与对账物"，不是"防杠声明"。

## 5. builder 使用

```bash
.venv/Scripts/python.exe docs/contest/report-draft/tools/build_docx.py \
    --module src/ch03-overview.md            # 单模块渲染到 out/ch03-overview.docx
.venv/Scripts/python.exe docs/contest/report-draft/tools/build_docx.py --all   # 合并整本+封面/目录/页码
```
