# 报告审核清单（审核子代理使用，主会话据此整改）

> 审核产出写到 `docs/contest/report-draft/review/round1-<scope>.md`，每条发现一行：
> `[级别] 模块/位置 | 问题 | 证据（文件:行 或 建议改法）`
> 级别：**MUST**（事实错误/编造数字/口径违规，不改就翻车）/ **SHOULD**（评分维度丢分点、跨章不一致）/ **NIT**（措辞/风格）。

## A. 事实核对（对照全仓库，最重要）

1. 逐个数字验源：题量（45/4/72/39/21/181）、覆盖矩阵实测值、难度分布、诱饵 188/188、金标准 0 错判、盲评 72 条、测试数、n 轮、CI 数值、延迟 p95……每个数字在报告里出现的位置 ↔ 仓库出处（README/dataset-card/CHANGELOG/stats 输出）逐一登记，找不到出处的标 MUST。
2. 机制断言验源：五态判定名单、七题型名单、六能力命名、四证据类别、三旋钮参数名、网关行为（改写/记账/退避）、沙箱白名单路径、temporal 拨钟行为、pass^k 分母口径——对照 docs/contracts/、设计文档、源码 docstring。
3. 判卷口径：全文不得残留"双评委/仲裁/JUDGE_B"表述（v2.0.0 已定版单评委；dual 仅历史别名）。检查 manifest 协议 id 沿用 dual 的解释是否出现且不被误读。
4. 版本口径：v2.0.0；deb/exe 对应关系如实（deb 最终版由 D 重打）。
5. 禁编造：所有 `〔待填〕` 必须是真实待补项（D 矩阵/截图/终版图），不得用待填掩盖本可查证的数字。

## B. 跨章一致性

1. 术语表统一（以 README/契约为准）：六能力中文名、题包名（full/chains/challenge-v2/development-v2/gen）、"规则+单 LLM 评委"、"质检三件套"、适配器数（9）、四家被测对象名单。
2. 图/表语义 ID 全书唯一、每图每表被正文引用、无孤儿图位；同一事实在两章出现时数字一致。
3. 章间衔接：每章开头导读是否接住上一章结尾；第四/五章交界（数据设计↔评分）不互相越界重复。
4. 摘要数字=第七章数字（待填项两边同步）。

## C. 评分维度对账（对 outline §2 的表）

六维度（数据设计 25/自动评分 25/任务定义与通用性 15/稳定性与可复现 15/指标完整性 10/创新与工程落地 10）逐维检查：落点章节是否都有"硬证据段"（数字/图表/对照），缺的列 SHOULD。

## D. 格式与风格（builder 之外的）

1. 每图位状态标注与登记表一致；引用编号经渲染器替换后语义通顺（读 out/ 的 docx 或 src 的 ID 引用）。
2. 匿名扫描：学校/姓名/导师/个人路径/主机名/凭据零出现。
3. 三段式骨架抽查：每章至少 3 个技术小节符合"痛点→方案→证据"。
4. 说人话抽查：术语堆砌、连续超 8 句段落、空话段落列 NIT。
