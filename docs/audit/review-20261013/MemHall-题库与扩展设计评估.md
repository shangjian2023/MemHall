# MemHall 题库与扩展设计评估

> 后续实现：本评估的建议已由本轮实现推进，当前状态与命令以 [题库与扩展使用说明](../../benchmark-v2.md) 为准；本文件保留当时的问题诊断。新增公开测试／开发实例并不代表完成真实智能体区分度或人工校准实验。

评估日期：2026 年 10 月 13 日（北京时间）。依据：本地工作树、当日重新下载的官方命题与赛程，以及 benchmark 作者的论文和官方仓库。本文是设计评估与实施建议；建议中的协议、插件和新题库尚未实现。原作品介绍 Word 与正式题库保持各自的历史记录。

## 1. 结论与参赛定位

现有题库足以展示评测流程与核心机制；支撑稳健榜单及高质量的数据设计，独立场景、长程压力与行为验收仍偏薄。优先补强可证明的场景覆盖与扩展协议，随后扩大可校验的生成实例。单纯增加路径、随机代号或 paraphrase 的数量，不能直接增加同等数量的独立评测情形。

命题没有规定几千题的最低规模。官方要求样本具有区分度、覆盖面和扩展空间；数据设计质量与自动评分能力各占 25%。任务通用性 15%、稳定性与复现 15%、指标完整性 10%、创新及落地 10%。要求少量可执行样例，但样例交付与完整题库的评测充分性应分别论证。[S1]

建议定位：面向 openKylin 的长期记忆系统评测框架，重点衡量记忆如何在真实行动、文件产物、敏感信息边界与系统事件中发挥作用。六维能力、统一证据结构、运行封印及 OS 场景已经构成基础；接下来需要可替换题库协议与可信的数据、评分验证。

## 2. 本次直接清点的题库

| 集合 | 用例 | 全部探测 | 计分 / 诊断 | 当前作用 |
|---|---:|---:|---:|---|
| full | 45 | 87 | 66 / 21 | 六维主评测集 |
| chains | 4 | 13 | 10 / 3 | 多会话任务链补充 |
| gen | 21 | 42 | 26 / 16 | 公开模板生成池 |
| heldout（本地） | 21 | 42 | 26 / 16 | 与 gen 同生成器的另一组实例 |

正式口径 full + chains 共 49 用例、76 个计分探测；公开题库加 gen 共 70 用例。quick 是从 full 引用的 6 个 ID，不增加独立样本。heldout 不进入发行包，但公开 seed 与生成器仍允许重构，其威胁模型应继续如实披露。

本次清点发现：full 的 36 个能力×内容覆盖格中，30 格只有 1 题，3 格有 2 题、3 格有 3 题。每能力仅 6–9 题；reuse 的计分探测只有 7 个。全有效时，一次探测翻转就影响该维约 14.3 个百分点。应把覆盖格填满、同类场景多样性、难度与区分度分别验证。

gen 的 21 题中，路径 15 题、敏感信息 3 题、事实 3 题；偏好、模板、项目状态没有生成实例。生成器当前有 persist / recall / update / discriminate / boundary / temporal / reuse 七个分支，并有干扰密度、拨钟间隔与相似度旋钮。难度标签是族级标称，旋钮存在并不意味着难度已经实证标定。

full 的输入剧本文本长度为 33–361 字符，中位数 69；gen 中位数 72，chains 中位数 125.5。这里仅累加 user/task 字符串，不含智能体回复、系统提示或工具轨迹，不能把它等同于总上下文长度。该数据仍表明用户注入与干扰材料很短，长历史、竞争事实与渐进积累压力需要单列测试。

chains 中 3 题有 3 个阶段，1 题有 6 个阶段；只覆盖 persist/reuse 两维。多个现有真实适配器逐消息启动进程，数据中的会话边界与真实会话上下文并不完全等价。新增长链前，先明确适配器的会话能力及消息、会话、跨会话三个层级。

当前四轮重跑提供随机性证据，不增加独立题目。更多轮数可以估计同题波动；更多独立故事和题族才能检验对新场景的推广性。

## 3. 主流 benchmark 怎样设计

以下数量对应作者当前公开的具体数据或版本，各榜的样本单位不同。下面的规模不能直接合成统一排名，也不代表本项目需要复制相同数量。

| Benchmark | 公开规模或设计单位 | 核心设计 | 可借鉴点 |
|---|---|---|---|
| LongMemEval | 500 个高质量问题 | 五类能力；S 约 115k tokens、M 约 500 历史会话；有 oracle 证据条件 | 每题包含问题、答案、历史、答案位置，比较不同历史长度与检索条件 [S2] |
| LongMemEval-V2 | 451 个人工构建的问题 | 网页与企业环境中的多模态 agent 运行轨迹；最多 500 条轨迹、115M tokens 的历史 | 当前已有更丰富的历史和信息源设计，不能把旧版视为唯一现状 [S3] |
| LoCoMo | 长会话是数据主体；平均约 300 轮、9k tokens，最长 35 会话 | 基于人物与时间事件构造会话；QA、事件总结、对话生成；QA 五类 | 多会话时间结构与证据定位比短问答换词更重要 [S4] |
| MemBench | 论文统计为约 5.3 万问题，精确比较需固定发布 split | 事实记忆、反思记忆，参与型与观察型记忆，多场景与角色 | 区分记住事实与从经历总结偏好；规模需要配套标注和质量校验 [S5] |
| MemoryAgentBench | 按长序列增量输入，而非每题重新给全部历史 | 准确检索、测试时学习、长程理解、选择性遗忘 | 明确记忆形成过程，检验增量更新与冲突处理 [S6] |
| MemoryArena | 连续的环境交互任务，网站列出网页搜索、购物、旅行规划、数理推理 | 前一个子任务产生后续所需的信息，行动与环境反馈构成记忆历史 | 以任务成功和记忆复用衡量 agent，贴近本赛题的行动验收 [S7] |

LoCoMo 的平均长度以作者项目页为准；本文未通过原始 JSON 复点问题总数，因此没有把常见的 QA 精确数量当成本次清点结果。MemBench 的约数来自原文 Table 2；合成问答实例与独立人物、故事、会话或题族需要分别统计。

“9600 族”未定位到可核验的群内原始材料，无法判定其单位。需要核对它指独立任务族、题目实例、探测点，还是实例×模型×轮次的执行数。示例：32 个模板×30 个取值×10 个扰动可以生成 9600 实例；这个算式不构成 9600 个独立题族，也不是对具体竞品的断言。

## 4. 与赛题相比，当前最需要补的证据

| 优先级 | 缺口 | 本项目的现状 | 可验收的补强 |
|---|---|---|---|
| P0 | 独立情形与区分度 | 覆盖矩阵完整，但多数格只有 1 题；生成池偏路径 | 新题体现不同冲突、作用域、有效期与行动结构；按题族统计，报告难度、天花板与地板效应 |
| P0 | 评分校准 | 有规则、LLM、锚例、离线自测与抽检工具；现有正式实测只有评委 A | 完成一批盲评人工标签，覆盖六维及主要错误类；披露一致率、误判与待复核率 |
| P0 | 行动复用的事实证据 | reuse 有文件断言；真实 actions 覆盖不完整 | 验证目标路径、文件内容、错误旧路径、步骤与操作结果；限定证据覆盖，不因答“完成”就给分 |
| P0 | 题库替换后的可比性 | 有 YAML 数据模型、案例快照、封印与源指纹 | 增加 suite/family/split 身份、评分协议版本、分母政策；阻止不同题库协议静默混入同一榜单 |
| P1 | 长程信息积累 | 多数输入短；已有 16 条事实压力题与 4 条链 | 多会话、信息竞争、延迟提问、多次改口、实体相似、带有效期的历史 |
| P1 | 独立留出 | 另一 seed 仍复用相同模板和槽位池 | 按故事/模板族隔离 dev 与测试，替换实体词表和表达方式；需要隐藏评测时私有保管实际测试包 |
| P1 | 记忆贡献的因果对照 | mock 是工程测试桩，不能替代无记忆基线 | 同一模型与预算下比较关闭长期记忆、正常记忆、oracle 证据条件，注明各条件改变什么 |
| P1 | 社区扩展的成本 | 适配器统一注册表；规则和指标以内置实现为主 | 至少演示一个无需改 runner 的外部题包；再逐步提供外部适配器、评估器与指标注册契约 |

judge_audit_sample.py 是抽检工具，只有生成工作表不等于人工校准已完成。评委与被测者使用同模型标识的偏倚需披露；更换评委 B 后仍需验证可靠性。动作与文件证据也要注明完整、部分或不支持，不能把缺少证据记成成功。

已有公开成绩支撑对本批样本的描述。按题聚类复核与样本数应限制排名结论；增加随机变体或重复执行不应直接当作独立样本扩大显著性。

## 5. 可替换、可插拔：已有基础与缺少的协议

| 接口层 | 已有实现 | 建议增加 |
|---|---|---|
| 题库输入 | CLI -c 接受 YAML 目录；MemoryCase / probe schema | 独立题包 manifest；版本、来源、许可、split、family、预期证据能力与计分协议 |
| 智能体接入 | AgentAdapter 抽象接口与统一 ADAPTERS 注册表 | 外部配置或安装包注册；会话、文件、记忆、动作的能力声明与验收 |
| 评分 | 规则断言与 LLM judge | evaluator 类型与版本注册；标注证据要求和评分返回结构；新增断言无需改中央分发逻辑 |
| 指标 | 六维、按探测/按题口径及多轮聚合 | 指标配置、权重、未决处理、分母与置信区间的协议标识 |
| 追踪 | case 快照、manifest、hash 封印及源指纹 | suite 与评分协议指纹；比较前检查兼容性，变更后显示独立版本结果 |

推荐最小题包约定：suite_id、suite_version、schema_version、family_id、split、generator_version、seed、variant_params、required_evidence、scoring_protocol、case/probe 清单与内容 hash。既有 meta.generator 可以承载部分生成元数据，但当前生成 YAML 只保存 name/version，没有完整留存 seed、取值与旋钮。

题族应表示一种相对独立的情形结构，例如“多次更新后按有效日期查询”，而非仅把六能力名称当成六个题族。一个 family 可有多个实例；统计时先聚合实例，再按 family/能力汇总，避免某个易生成模板主导总分。具体权重必须预先固定并公开。

扩展前先建立最小演示：把一份新题包放入独立目录，完成校验、发现、运行、归档、重渲染与对比；没有业务代码变化也能接入题包。外部 Python 插件是后续工程选择，赛题并没有强制要求某一种插件加载机制。

外部 LongMemEval/LoCoMo 数据可作为独立导入题包，用于检索和时间能力测试。QA 导入后的分数应保留原任务语义；不能声称它直接覆盖了 openKylin 文件执行、敏感持久化或行动复用。

## 6. 题库扩充方案

建议分层并分别报告：smoke（现有 6 题）、core-v1（冻结现有 full+chains 49 题）、challenge-v0.2（新建独立挑战集）、generated-stress（规模化变体）、heldout（按故事族隔离的受控测试集）。每层写明样本、探测、题族、运行与预算单位。

短期目标：先构建 36–72 道经过校验的 challenge 题，覆盖六维，重点加强更新、边界、复用和跨会话信息竞争。补 8–12 条能验收真实产物的长链。前述数量是设计目标，必须依据实际编写、lint、人工审核及真实运行完成度报告；未运行的新题不应加入正式榜单成绩。

中期目标：合理的 36 格各有 3–5 个不同故事，即约 108–180 个独立基础场景；允许对不合理组合做有解释的取舍。每个故事再有实体、路径、表达、干扰、间隔和相似度变体，形成 500–2000 个压力实例或更多。生成数量与已审核、已运行的数量分别披露。

| 新场景族示例 | 实际增加的难点 | 最小验收 |
|---|---|---|
| 三次版本更新 | A→B→C，多次改口；问现在与历史日期分别得到不同答案 | 语义答案、旧值复用错误、有效日期 |
| 同名实体与作用域 | 两位用户、两个项目与相似路径同时存在 | 正确归属，不串用户或项目 |
| 临时信息有效期 | 一次性口令、当天目录与长期偏好并存 | 需要记的保留，不该持久化的未保存、不复用 |
| 长历史与事实竞争 | 分阶段积累大量有效事实，中间包含有意义的竞争信息 | 指定事实检索、证据位置、在不同负载下的曲线 |
| 默认偏好复用 | 只在早期出现格式偏好，后续自然任务不点名提示记忆 | 最终文档格式、内容与目标位置 |
| 环境迁移与路径更新 | 项目搬迁，旧路径仍存在；新任务必须使用最新路径 | 新文件及内容 hash，旧路径没有被错误写入 |
| 任务链的中间产物 | 先生成模板、再更新规则、最后跨会话完成文档 | 各阶段输出与最终成品可追溯 |
| 来源冲突与风险边界 | 用户要求与网页/文件中的不可信指令产生冲突 | 不可信内容不成为持久规则，不导致错误行动 |

每个基础场景至少提供正确、遗漏、混淆/旧值、拒绝或过度保存等适用锚例；并不是每个场景都应机械套全体错误类。对照改变一个因素，其余剧本、取值与评分标准固定，才能说明难度旋钮的作用。

评分抽检建议：先完成 60–100 个判决的分层人工复核，按六维及高风险错误类抽样；开发校准与独立测试分开，避免在同一批题上调 rubric 又宣布校准成功。这是建议规模，不是已完成的审计结果。

## 7. 截止前的实施顺序与验收

官方赛程在 2026-10-13 重新获取，截止为 2026 年 10 月 16 日 24:00（北京时间）。建议把有限时间集中到能出示证据的修改，代码能力与实验能力分别验收。[S1]

1. 冻结历史 core-v1 与旧结果；给现有题包补清晰的数据、评分与版本身份。
2. 完成一个新题包的接入演示，记录配置、清单、内容 hash 和结果兼容检查。
3. 优先写并校验更新、边界、复用与长链挑战题；以 36–72 题为设计目标，依实际进度缩小并如实标注。
4. 在至少两款真实智能体上跑经过审核的固定子集，使用同一题包、模型政策、预算与判卷配置；分别报告新集与历史集。
5. 完成一批盲评校准，提交错误案例、可靠性限制及有效分母。
6. 重建并验收修复版本的 deb，核对实际 openKylin 录屏。官方要求至少两款真实智能体的完整评测和多维对比雷达图，建议 3–5 分钟。[S1]

标准环境二进制、历史归档缺口、独立评委校准与视频属于原审计已标记的交付事项；本文没有据此宣称它们已被本轮修复。提交时应以最新验收证据逐项更新，避免旧包和新源码的行为混写。

## 8. 提交材料的措辞建议

可以强调：六维能力定义、结构化剧本、评分与诊断分离、真实运行证据、可追踪封印、可复现抽样、openKylin 的系统事件和文件产物验证；扩展方案写成已经实现的部分、经演示的部分、后续规划三个状态。

应限制或补证的表述：稳健全局排名、数千个独立题族、真正不可见的 heldout、完整动作证据覆盖、已完成双评委校准、离线云模型推理、多日真实时间压力，以及“接入任意 agent 不需开发”。这些表述只有达到对应实际条件后才适合写进作品介绍。

建议主张：MemHall 以真实运行证据衡量长期记忆的保持、调用、更新、区分、边界与复用，并用版本化题包承载可持续扩展。待最小题包协议实现并验证后，再把后半句列为已实现能力。
